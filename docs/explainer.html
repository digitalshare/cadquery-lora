Text to CadQuery, explained

What we are training today, how the pieces fit, and how we will know whether the small open model beat the closed one.

1. The task

A user describes a mechanical part in plain English. The model must answer with CadQuery, a Python library for building 3D solids. We run that code, export the mesh, and compare it to the real part. Nothing is judged by opinion: the code either runs or it doesn't, and the shape is either close to the ground truth or it isn't.

Why this task is a good hackathon pick

  • The reward is mechanical. Execution rate and shape distance are computed by a script, so judges cannot argue with the eval.
  • Frontier models are only okay at it. CadQuery is a niche API; closed models invent methods that do not exist.
  • 170k verified examples exist. The Text2CAD corpus pairs descriptions with code that provably rebuilds the part.

2. What "fine-tuning" changes

We do not train a model from scratch. We start from Qwen 3.6 35B-A3B, an open model that already writes Python, and nudge it toward CadQuery with a few thousand worked examples. The base weights stay frozen. What we train is a LoRA adapter: a small set of extra matrices bolted onto the attention and MLP layers. The adapter is about 0.3% the size of the model, which is why training takes minutes and dollars, not days and GPUs you own.

3. The workflow, end to end

Everything on the left runs on this laptop; everything on the right is Fireworks. The laptop never touches a GPU: it sends token batches up and gets gradients applied remotely.

4. Fireworks pieces, and which path we used

Fireworks offers two ways to fine-tune. Managed training is the point-and-click one: upload a JSONL dataset, pick a base, press go. Serverless training hands you the training loop as Python and bills per token, with no dataset upload and no deployment required to test. Managed was blocked on this account today (dataset uploads disabled, deployments need a payment method), so we took the serverless path.

Session
A reservation in the shared trainer pool. Each account gets 8 concurrently. Delete it when done or it keeps the slot.
Run
One training client inside a session: base model + adapter config (rank, seed). Our run id is run-04415322249b49f0977058f0d3373dfc.
forward_backward
Send a batch, get the loss gradient applied remotely. We call it with "cross_entropy" and per-token weights.
optim_step
Apply the accumulated gradient with Adam at the current learning rate. We use a short warmup then cosine decay.
Sampler checkpoint
Adapter weights frozen at a step, addressable as account/run/name. Anyone with the key can sample from it, even after the run ends.
Promote
Turn a sampler checkpoint into a regular model in your account, deployable with live merge.

5. How we score, and the bar to beat

Every model gets the same 300 held-out parts from the TextCAD-Bench test split (no overlap with training), the same system prompt, and two prompt styles: an abstract one-liner, and the expert spec with coordinates that a real CAD pipeline would hand over. Five numbers come out.

Tuned-model latency is from a separate idle-pool measurement (60 parts); the other rows were measured in their own runs. "Usable" means the code executed and the shape is within Chamfer 10 of the ground truth: a part an engineer would accept as a starting point.

Fine-tuning took execution from 54% to 97% on abstract prompts and from 8% to 94% on expert prompts. On usable parts the tuned 3B-active model lands a few points under Opus (39% vs 43% abstract, 31% vs 37% expert) at 15 to 23 times lower cost and lower latency, and it is the only open model that works on expert prompts at all. Haiku 5.5 is the honest competitor: on abstract prompts it has a similar price and a higher usable rate, so our edge is latency only; on expert prompts it has the higher usable rate (38% vs 31%) while we answer 3.7 times faster and deliver more usable parts per dollar (456 vs 418).

Two things to notice. The expert prompts make every zero-shot model worse, because they use DeepCAD's coordinate conventions that nobody has seen; that is exactly what training on the paired code teaches. And the untuned open models mostly fail by inventing CadQuery methods (Workplane.scale, Vector.filter), which is a vocabulary problem fine-tuning fixes directly.

7. What the model actually produces

Two prompts, same models. The first is a benchmark part written in the dataset's own style; the second is free-form engineering prose. The tuned model nails the first and misreads the second, which is exactly what training on 6,400 dataset-style examples should produce: it learned the conventions of its data, not CAD prose in general. That is the next thing to fix with more diverse prompts.

loss is the average negative log-probability the model assigns to the correct next code token. 0.79 at step 1 means it was fairly surprised by the reference code; 0.19 means it now predicts most of it confidently. lr ramps up over 8 warmup steps, then decays along a cosine so the last steps make small, careful changes. A checkpoint every 25 steps lets us score early and pick the best one rather than trusting the final step blindly.
